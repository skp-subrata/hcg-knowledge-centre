# Deploying to Render

The app is a single Flask process with a SQLite file and an uploads folder, so on Render it runs as one **Web Service** with a **persistent disk**. Everything below is captured in `render.yaml`; the dashboard steps just point Render at it.

## Before you start

| you need | why |
|---|---|
| A Render account (https://dashboard.render.com) | hosts the service |
| The repo connected to Render, **or** its public URL | Render deploys from GitHub. Connecting gives auto-deploy on push; a public URL works without any GitHub authorisation but has no auto-deploy |
| A paid instance (Starter is enough) | persistent disks are not available on the free plan; without a disk the database and uploads are wiped on every deploy and restart |
| A password for the seeded `admin` account | set as `LMS_ADMIN_PASSWORD`; otherwise the first boot creates `admin` / `admin` on a public URL |

**Fork or not?** Render must be allowed to read the repository. If the repository belongs to someone else (`skp-subrata/hcg-knowledge-centre`), either the owner installs the Render GitHub app for it, or you fork it to your own account and connect the fork (`gh repo fork skp-subrata/hcg-knowledge-centre --clone=false`, then push `dev-akash` to the fork). Because the upstream repo is public you can also skip GitHub entirely: New → Blueprint → "Public Git repository" → paste the URL and choose the branch. The `gh` CLI is not involved in the deployment itself; Render pulls from GitHub on its own.

## Steps

1. **New → Blueprint**, select the repo (or paste the public URL) and the `dev-akash` branch. Render finds `render.yaml` and shows one web service with a 1 GB disk mounted at `/var/data`.
2. Set the one secret it asks for: `LMS_ADMIN_PASSWORD` (anything strong). `LMS_SECRET_KEY` is generated by Render.
3. Click **Apply**. The first build installs `requirements.txt` (a few minutes; `firebase-functions` pulls the Google Cloud SDK, remove it to cut the build time) and starts `gunicorn app:app`. First boot creates the tables, applies `init_scripts/*.sql`, seeds masters and release notes and, because `LMS_SEED_DEMO=1`, the demo accounts and courses.
4. Open the service URL. Sign in as `admin` with the password you set; `mod`/`mod` and `student`/`student` exist too, so change or deactivate them from the admin workspace before sharing the URL.
5. Once you have real data, set `LMS_SEED_DEMO=0` in the dashboard (Environment) so restarts stop re-seeding demo content.

## What the environment variables do

| variable | value on Render | purpose |
|---|---|---|
| `LMS_DATABASE` | `/var/data/users.db` | SQLite file on the persistent disk |
| `LMS_UPLOAD_FOLDER` | `/var/data/uploads` | course files, attachments, profile pictures |
| `LMS_SECRET_KEY` | generated | session signing; stable across deploys so users stay logged in |
| `LMS_PROXY_FIX` | `1` | trust Render's `X-Forwarded-*` headers so the app sees `https://` and the right host |
| `LMS_SECURE_COOKIES` | `1` | session cookie only over HTTPS |
| `LMS_CSRF` | `1` | CSRF tokens on every form |
| `LMS_DEBUG` | `0` | no debugger or reloader in production |
| `LMS_SEED_DEMO` | `1` then `0` | demo data on first boot only |
| `LMS_ADMIN_PASSWORD` | your secret | password given to the seeded `admin` account |
| `PORT` | set by Render | gunicorn binds to it |

## Operating notes

- **Backups**: the disk is the only copy of your data. Use Render's disk snapshots, or add a cron job that copies `/var/data/users.db` to object storage.
- **Scaling**: keep `--workers 1`; SQLite serialises writes and the threads handle concurrent readers. If you outgrow that, move to Postgres (the queries use standard SQL, but `INSERT OR IGNORE`, `GROUP_CONCAT` and `sqlite_master` would need porting).
- **Uploads up to 100 MB** are allowed by the app; Render's proxy allows that size but slow clients may hit the 120 s gunicorn timeout, which is why `--timeout 120` is set.
- **Logs**: the app logs to stdout; Render shows them under Logs. Set `LMS_DEBUG=0` always.
- **Health check**: `/api/v1/releases/active` is public and cheap.

## Other hosts

The same settings work on any container platform: build `pip install -r requirements.txt`, run `gunicorn --bind 0.0.0.0:$PORT --workers 1 --threads 8 app:app`, mount a volume for `LMS_DATABASE`/`LMS_UPLOAD_FOLDER`, set `LMS_PROXY_FIX=1` behind a TLS proxy. `docs/cloud_hosting_architecture.md` sketches a larger Cloud Run / ECS layout.
